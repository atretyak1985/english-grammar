# Промпт для Claude CLI — розмітка минулих часів у бібліотеці

Цей документ — для оператора, який додає нове оповідання в
`src/content/library/<slug>/`. Він не автоматизований і не читається кодом:
скрипт засіву (`scripts/seed-library.mts`) до Anthropic не звертається взагалі
(SC-9) — розмітку приносить людина через Claude CLI, а скрипт лише перевіряє й
записує готовий артефакт.

Результат цього процесу — файл `matches.json` у форматі, описаному нижче.
Перш ніж вважати оповідання готовим, прогоніть його крізь
`npm run db:seed` (або `make db-seed`): валідатор (`src/lib/library/
artifact.ts`) або прийме файл, або назве точну причину відмови — перелік цих
причин наприкінці документа.

> **Спершу спробуйте `make import-book`.** `scripts/import-book.mts` робить
> кроки 1 і 2 цього документа — нарізку на шматки й наскрізну нумерацію слів —
> тим самим кодом, що читалка, тому найнебезпечнішої помилки (зсув нумерації)
> там не може бути за побудовою. Розмітку він бере з локальних правил, а з
> `--review` уточнює моделлю. Цей документ потрібен, коли розмітку робите
> руками через Claude CLI: він описує формат `matches.json`, правила вибору
> часу й причини, з яких засів відмовляє.

## 1. Нарізка на шматки

Модель розбирає текст частинами, як і застосунок (`src/lib/analyzer/
chunks.ts`, `chunksOf`): шматок набирає **1500 слів**
(`CHUNK_WORDS`), а потім росте до найближчого кінця речення — крапки, знака
питання чи оклику (разом із закривними лапками й дужками після нього). Якщо
кінця речення не трапилось ще довше — шматок обрізається жорстко на
**2000 словах** (`CHUNK_MAX_WORDS`), навіть посеред речення.

Це та сама межа, яку рахує `chunksOf()` над готовим текстом — саме тому
скрипт засіву може перевірити її сам (перевірка 4 нижче), без участі моделі.
Якщо ви ріжете текст руками, а не інструментом, звіряйте межі шматків із
`chunksOf(tokenize(story))`: розбіжність хоч на одне слово — це вже провалена
перевірка.

## 2. Наскрізна нумерація слів — ЖОРСТКА ВИМОГА

**Слова нумеруються з 1, наскрізно по всьому оповіданню, а не всередині
шматка.** Другий шматок НЕ починається знову з 1 — він починається з номера,
на якому закінчився перший (`firstWord` другого шматка = `lastWord` першого +
1).

Коли просите Claude розібрати другий (і кожен наступний) шматок, скажіть йому
явно, з якого номера почати рахунок — тобто вставте в промпт нумеровані слова
цього шматка вже зі зсувом, а не з нуля. Наприклад, якщо перший шматок
закінчився на слові 1500, у промпті для другого шматка перше слово підписане
як `1501:<слово>`, а не `1:<слово>`.

Це найважливіший пункт документа. Зсув нумерації на всього ОДНЕ слово
розмічує не ту конструкцію на весь залишок оповідання, і на око це майже
непомітно — саме тому перевірка 5 нижче існує окремо, як пастка на цей
конкретний випадок.

## 3. Що вважати Past Simple / Continuous / Perfect

Ті самі правила, які застосунок ставить перед моделлю в синхронному розборі
(`src/lib/analyzer/review.ts`, константа `SYSTEM`). Коротко:

- **ps (Past Simple)** — фінітне дієслово в минулому часі: `walked`, `went`,
  `was`, `did not go`. `was`/`were` як ГОЛОВНЕ дієслово («she was tired») —
  теж `ps`, і конструкція охоплює лише сам токен `was`/`were`.
- **pc (Past Continuous)** — `was`/`were` (+ `not`) + дієслово на `-ing`.
- **pp (Past Perfect)** — `had` (+ `not`) + дієприкметник минулого часу,
  включно з Past Perfect Continuous («had been working»).

Не позначати: дієприкметники-прикметники («a tired engineer», «an interested
reader»), Present Perfect («have finished»), пасив у теперішньому часі,
інфінітиви, іменники, що просто закінчуються на `-ed`. `had` перед іменниковою
групою — це Past Simple від «have» («I had lunch»), позначається `ps` на
самому токені `had`, а не `pp`.

Одна конструкція — один збіг: перше слово (`допоміжне`, якщо воно є) і останнє
слово (`смислове`) тієї самої конструкції; прислівник між ними («had never
seen») лишається ВСЕРЕДИНІ меж. Найдовша реальна конструкція — 4 слова («had
not been working»).

Приклади (номери тут — з нуля, як у внутрішньому форматі моделі; у вашому
промпті вони будуть зі зсувом за пунктом 2):

```
Input: 0:A 1:tired 2:engineer 3:had 4:lunch 5:and 6:left.
  {from: 3, to: 3, ps} — «had» тут дієслово «мати», об'єкт «lunch» лишається зовні.
  {from: 6, to: 6, ps} — «left», неправильна форма.
  «tired» НЕ позначається — це прикметник, а не дієслово.

Input: 0:She 1:had 2:never 3:seen 4:it, 5:so 6:she 7:was 8:waiting.
  {from: 1, to: 3, pp} — «had ... seen», прислівник «never» усередині меж.
  {from: 7, to: 8, pc} — «was waiting».
```

## 4. Формат `matches.json`

```json
{
  "format": 1,
  "seededBy": "claude-cli",
  "seedModel": "claude-opus-5",
  "chunks": [
    {
      "index": 0,
      "firstWord": 1,
      "lastWord": 1500,
      "matches": [{ "word": 12, "length": 2, "tense": "pc" }]
    },
    {
      "index": 1,
      "firstWord": 1501,
      "lastWord": 2057,
      "matches": []
    }
  ]
}
```

Поля:

- `format` — завжди `1`.
- `seededBy` — `"claude-cli"` для розмітки через цей промпт (для смоук-прикладу
  локальними правилами використовується `"local-rules"`).
- `seedModel` — модель, якою розмічено (необов'язкове поле).
- `chunks[].index` — порядковий номер шматка, з 0, у тому самому порядку, що
  дає `chunksOf`.
- `chunks[].firstWord` / `lastWord` — межі шматка в номерах слів (з 1,
  наскрізно).
- `matches[].word` — номер ПЕРШОГО слова конструкції, з 1.
- `matches[].length` — скільки слів у конструкції (мінімум 1, максимум 4).
- `matches[].tense` — `"ps"` | `"pc"` | `"pp"`.

Жодних інших полів парсер не приймає — на будь-якому рівні, невідоме поле
валить засів так само, як зсунута нумерація.

## 5. Чому засів впаде — і на якому саме кроці

`npm run db:seed` перевіряє кожне оповідання перед записом
(`parseArtifact` → `toTokenMatches` → `validate`). Ось усі причини відмови, у
тому порядку, в якому їх перевіряє код — з назвою файлу й конкретним
діапазоном у повідомленні:

1. **Межі виходять за текст.** Слово з номером, більшим за кількість слів в
   оповіданні (або `word + length - 1` виходить за цю межу) — майже завжди
   помилка нумерації в кінці шматка.
2. **Діапазони перетинаються.** Дві конструкції претендують на той самий
   токен — модель не мала повертати перекриття, а якщо оператор склеював
   відповіді кількох запитів руками, перевірте межі шматків.
3. **Невідомий `tense`.** Будь-яке значення поза `"ps" | "pc" | "pp"` —
   зазвичай друкарська помилка або застаріла назва часу.
4. **Межі шматків не збігаються з `chunksOf`.** `firstWord`/`lastWord`
   кожного шматка мають дорівнювати тому, що дає `chunksOf(tokenize(story))`
   на цьому ж тексті, і кількість шматків має збігатися. Якщо ви різали текст
   не тим самим кодом, що читалка (наприклад, руками по абзацах) — ця
   перевірка впаде першою, і саме вона найточніше назве причину.
5. **Замало підтверджень очевидних Past Simple.** Скрипт бере явні збіги
   локальних правил (`findMatches`) і дивиться, яку частку з них підтверджує
   ваш артефакт (перетином діапазонів, не точною рівністю — модель законно
   розширює межі, наприклад «had never seen»). Якщо підтверджено менше 60 %
   — це майже завжди зсув нумерації слів на весь текст (пункт 2 вище), а не
   інша думка моделі про межову конструкцію.

Перевірка 4 виконується перед перевіркою 5 навмисно: зсунута нарізка шматків
дає обидві помилки одночасно, а перша називає причину точніше.
